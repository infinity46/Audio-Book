# Prisma migrations — Audiobook Production Platform

This directory holds the Prisma schema (`schema.prisma`) and the SQL migrations derived from
it. The persistence contract of record is
[`docs/architecture/database-schema.md`](../docs/architecture/database-schema.md)
(`db-schema.v1.1`). `schema.prisma` is derived from that document, never the reverse
(`database-schema.md` §36, §45 rule 2), and this README documents where the two diverge because
Prisma's schema language cannot express part of the contract.

## 1. Running migrations

```
pnpm prisma:migrate:deploy
```

This runs `prisma migrate deploy --schema prisma/schema.prisma`, defined in the root
`package.json`. It applies `prisma/migrations/0001_init/migration.sql` (and any later migration)
against `DATABASE_URL`.

**Migrations are never run automatically by an application process at startup.** This is a hard
rule from `deployment-architecture.md` and is restated in `database-schema.md` §45 rule 19:
_"never run migrations from an application process."_ Every service **refuses to start** on a
database that isn't already at the expected schema version rather than attempting to migrate
itself. `prisma:migrate:deploy` is run explicitly, once, from the deployment pipeline, using the
`app_owner` role (§37.2) — the only role permitted to run DDL. No API instance, worker, or job
process ever holds `CREATE`/`ALTER`/`DROP` privileges.

## 2. What's in `0001_init/migration.sql`, and why

The bulk of `migration.sql` (`CREATE TYPE`, `CREATE TABLE`, ordinary indexes, plain foreign keys)
was mechanically generated by `prisma migrate diff --from-empty --to-schema-datamodel` from
`schema.prisma`, and is a faithful translation of what Prisma's schema language can express.

A block appended after that base DDL (marked `-- APPENDED: everything Prisma's schema language
cannot express`) adds everything the base DDL is missing. `schema.prisma` itself flags every one
of these locations inline with a comment ending in "...lives in migration.sql" / "...is added in
migration.sql" / "...declared in migration.sql, not here" — run
`grep -n "migration.sql" prisma/schema.prisma` to find them. Three further edits were made
**in place** to the base DDL, each documented at the point it occurs and summarized again here,
because they are the only exceptions to "purely additive, appended after":

1. **Extension bootstrap, prepended before the first `CREATE TYPE`.** `CREATE EXTENSION IF NOT
EXISTS "vector"` must run before the base migration's own
   `CREATE TABLE "narrative_embedding" (... "embedding" vector(1536) ...)`, because Prisma
   emitted the raw `vector(1536)` type literally from `Unsupported("vector(1536)")` in
   `schema.prisma`, and a `CREATE TABLE` referencing an unknown type fails immediately. This
   makes strict "append only" impossible for pgvector specifically. `citext` and `btree_gist`
   have no such ordering requirement (both are used only in the appended section) but are
   bootstrapped in the same block for one obvious place to look, rather than splitting extension
   setup across the file.
2. **`audit_log`'s `CREATE TABLE` statement**, edited to add `PARTITION BY RANGE ("occurred_at")`
   and to widen the primary key from `("id")` to `("id", "occurred_at")` — PostgreSQL requires the
   partition key to be part of every unique/primary-key constraint on a partitioned table. See
   §5 below for the tradeoff this forces.
3. **`user.email`**, widened from `TEXT` to `CITEXT` via `ALTER TABLE "user" ALTER COLUMN "email"
TYPE CITEXT` in the appended section (not in place — unlike `vector`, nothing downstream in
   the base DDL depends on the column already being `citext`, so the simpler, genuinely-additive
   `ALTER ... TYPE` after the base `CREATE TABLE` was preferred over editing the `CREATE TABLE`
   itself).

## 3. Prisma DSL limitations this migration works around

| Category                                              | Why Prisma can't express it                                                   | What's added                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Partial unique indexes** (`UNIQUE (...) WHERE ...`) | Prisma's `@@unique` has no `WHERE` clause                                     | ~14 partial unique indexes: `is_current` version-chain uniques (six tables per §4.2), `book_file` tenant dedupe, `book_version` structural-ingest idempotency, `character` sentinel, `voice_profile` name-per-scope, `voice_assignment` active-per-role, `chapter_audio` manifest + current, `audiobook` current, `audio_script`/`audio_script_chunk`/`audio_chunk` current, `processing_job` idempotency key |
| **Exclusion constraints**                             | Not a Prisma concept at all                                                   | `character_alias`'s range-overlap exclusion (`EXCLUDE USING gist (...)`), requiring `btree_gist`                                                                                                                                                                                                                                                                                                              |
| **CHECK constraints**                                 | Prisma has no `@check`/`@@check` in this Prisma version                       | 52 CHECK constraints: the content-hash hex-format contract (§4.3, on every `*content_hash` column — 26 of the 52) plus every architecturally load-bearing CHECK named in §25.1 and the individual per-entity write-ups (consent attestation, lock-state, coverage invariant, bytes-exist invariant, AI-disclosure, sentinel consistency, and more)                                                            |
| **Generated/computed columns**                        | No `GENERATED ALWAYS AS ... STORED` support                                   | `audio_script_chunk.has_review_flags`, `audio_chunk.has_capability_gap`, `character_alias.scope_key`                                                                                                                                                                                                                                                                                                          |
| **The `vector` type**                                 | pgvector isn't a Prisma type                                                  | Column already emitted via `Unsupported("vector(1536)")`; this migration adds the extension and the HNSW index                                                                                                                                                                                                                                                                                                |
| **`citext`**                                          | No case-insensitive text type in Prisma                                       | `user.email` widened via `ALTER COLUMN ... TYPE CITEXT`                                                                                                                                                                                                                                                                                                                                                       |
| **`NULLS NOT DISTINCT`** (PostgreSQL 15+)             | Prisma cannot emit it                                                         | `job_dependency` and `audiobook_rendition` unique constraints                                                                                                                                                                                                                                                                                                                                                 |
| **`DEFERRABLE` constraints**                          | Prisma constraints are always `NOT DEFERRABLE`                                | `chapter`'s `(book_version_id, order_index)` unique, `DEFERRABLE INITIALLY IMMEDIATE`, so a reorder can renumber inside one transaction                                                                                                                                                                                                                                                                       |
| **Table partitioning**                                | No partition support at all                                                   | `audit_log PARTITION BY RANGE (occurred_at)`, monthly partitions                                                                                                                                                                                                                                                                                                                                              |
| **Composite FK with differing nullability**           | Prisma's `@relation` composite FKs require matching nullability on both sides | `audio_chunk (audio_script_chunk_id, character_id) → audio_script_chunk (id, character_id)`, keeping the denormalised `character_id` honest                                                                                                                                                                                                                                                                   |
| **Functional/expression indexes**                     | No `lower(col)` index support                                                 | `book`, `voice_profile` (`lower(name)`/`lower(title)`) partial indexes                                                                                                                                                                                                                                                                                                                                        |
| **Named GIN indexes on JSONB**                        | Prisma has no GIN/`jsonb_path_ops` opclass support                            | The three §23.3 indexes: `audit_log.metadata`, `worker.capabilities`, `model_version.config`                                                                                                                                                                                                                                                                                                                  |

Also added, alongside the above, wherever the source document gave an exact predicate: the
non-unique partial performance indexes explicitly named in §13.2 (`audio_script_chunk`'s review
queue), §15.1 (`processing_job`'s five operational indexes, including "the single most important
operational index in the table" — the orphan-reaper index), §15.3 (`job_dependency`'s two),
§15.5 (`worker`'s quarantine index), and §16.2 (`audio_chunk`'s QC view index).

**Deliberately out of scope for this migration:** the remainder of §22's performance-index
inventory not named above — e.g. the other non-unique partial indexes on `character`,
`chapter_audio`, `tts_job`, and the full nine-index set each on `audio_script_chunk`/
`audio_chunk` beyond their uniqueness constraints. Those are query-serving indexes, not
correctness constraints; §22.5 requires every index to be justified by a named, measured query,
and several of those queries aren't implemented by any service yet. Add them in a follow-up
migration, `CONCURRENTLY`, once the query patterns exist (§22.5, §35.4).

## 4. Open questions and judgment calls

A human reviewer should double-check the following before this migration is treated as final:

1. **OQ-DB-12 (embedding dimension/distance metric, §44).** Neither `vector(1536)`'s dimension
   nor the HNSW index's `vector_cosine_ops` operator class is fixed by any architecture document.
   1536 is the placeholder already in `schema.prisma`; `vector_cosine_ops` is this migration's
   default choice for text-embedding similarity, not a transcribed value. A dimension change is a
   table rewrite and is Breaking (§11.8) — resolve OQ-DB-12 before Phase 6.
2. **`character_alias.scope_key`'s exact generation expression.** §10.2 specifies only that it's
   "a generated column combining `scope_kind` with its scope id," without giving the formula.
   This migration uses `'GLOBAL'` / `'CHAPTER:' || scope_chapter_id` /
   `'SPEAKER:' || scope_speaker_character_id`. It satisfies the exclusion constraint's need for a
   collision-free scope discriminator, but it is a transcription judgment call, flagged inline
   with `-- TODO(doc-ambiguous):`, not a value taken verbatim from the document.
3. **`audit_log`'s primary key is widened from `(id)` to `(id, occurred_at)`.** This is a direct,
   documented consequence of PostgreSQL's partitioning rules (§17.1 requires
   `PARTITION BY RANGE (occurred_at)`, and PostgreSQL requires the partition key in every
   unique/PK constraint) rather than a discretionary choice, but it does change what PostgreSQL
   itself can prove: `id` (an application-generated UUIDv7) is still unique in practice, but the
   database can no longer enforce that alone — only `(id, occurred_at)` together. Anything that
   was relying on `id` as a standalone unique reference into `audit_log` (there is currently
   nothing in `schema.prisma` that does) would need the pair.
4. **`audit_log` partition maintenance is not automated by this migration.** Only the current
   month's partition and the next month's are created (`audit_log_2026_08`, `audit_log_2026_09`,
   given the date this migration was written). No `DEFAULT` partition exists, so an insert dated
   outside the created partitions will fail loudly rather than silently landing in a catch-all —
   a deliberate choice (see the comment at the partitioning section in `migration.sql`), but it
   means a monthly partition-creation job (and eventually a retention job that `DETACH`es old
   partitions per §17.1/§27) must exist operationally before this table reaches its second month
   in production. Building that job is out of scope for this migration.
5. **OQ-DB-6 (role vocabulary, §44).** `principal_role`'s member list is carried over from
   `api-specification.md` §6.2 and is explicitly marked **provisional** there; it is used as-is
   in `schema.prisma` and this migration adds no constraint around it beyond what the enum type
   itself provides. Confirm before Phase 2 per §44.
6. **The full §22 performance-index inventory is intentionally incomplete** — see the "out of
   scope" note in §3 above. This is a scope decision, not an oversight: every omitted index is
   named in `database-schema.md` with an exact predicate and can be added mechanically later.
7. **`audiobook_rendition.status`** is stored as `TEXT`, not an enum — `schema.prisma` already
   flags this at the model (§16.7 lists a `status` column but names no enum type for it, and §24
   has no entry). Not something this migration changes, but worth surfacing here since it's
   adjacent to the `audiobook_rendition` constraints this migration does add.

## 5. Live-database validation

**Validated.** `docker compose up -d postgres` was run from the repo root (Docker Desktop was not
running by default in this environment and had to be started first); once `postgres` reported
`healthy` via its `pg_isready`-based healthcheck, the complete `migration.sql` — extension
bootstrap, base DDL, and the full appended section — was applied with:

```
docker exec -i <postgres-container> psql -U audiobook -d audiobook -v ON_ERROR_STOP=1 < prisma/migrations/0001_init/migration.sql
```

It applied cleanly end to end: **exit code 0, zero errors, zero warnings, zero notices.**

One real gap had to be worked around to get there: the stock `postgres:16.6-alpine` image used by
`docker-compose.yml` does not ship the `pgvector` extension (Alpine's `postgresql-pgvector`
package pulls in PostgreSQL 17 as a dependency, not 16). `pgvector` v0.7.4 was built from source
inside the running container against the image's own PostgreSQL 16 `pg_config`
(`postgresql16-dev`, `build-base`, `clang19` for the optional JIT bitcode) and installed to the
container's extension directory — a container-local, throwaway change, **not** a change to
`docker-compose.yml` or any other repo file. After confirming `CREATE EXTENSION vector` worked,
the database was reset (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;`) and the entire
migration was re-applied from a clean state to get the exit-code-0 result above. This means the
migration is verified correct against real PostgreSQL 16 semantics, but a from-scratch
`docker compose up` on this repo as committed will still hit the same missing-extension error
until either the Docker image is changed to one that bundles pgvector (e.g. `pgvector/pgvector:
pg16`) or an init step installs it — both are `docker-compose.yml` changes, which were explicitly
out of scope for this task.

Spot-checks performed against the resulting schema (all passed): `audit_log` is a partitioned
table with both partitions attached and PK `(id, occurred_at)`; `user.email` is `citext`;
`btree_gist`, `citext`, and `vector` all show in `\dx`; all three generated columns
(`has_review_flags`, `has_capability_gap`, `scope_key`) have the expected `GENERATED ALWAYS AS`
expression; `character_alias`'s exclusion constraint and its three CHECK constraints are present;
`chapter`'s sibling-order unique is `DEFERRABLE`/`INITIALLY IMMEDIATE`; both `NULLS NOT DISTINCT`
constraints report `indnullsnotdistinct = t`; the composite FK on `audio_chunk` is present; the
HNSW index and all three named GIN indexes exist (the GIN index on `audit_log.metadata`
correctly propagated to both partitions).

The database was left running (not torn down) after validation, per instruction, so the next
step (the schema-drift check) can use it.

## 6. Object count

This migration adds, beyond the mechanically generated base DDL:

- 3 extensions (`vector`, `citext`, `btree_gist`)
- 52 CHECK constraints (26 of them the `*content_hash` hex-format contract, §4.3)
- 14 partial unique indexes
- 22 partial/plain performance and GIN/HNSW indexes
- 3 generated (`STORED`) columns
- 1 exclusion constraint
- 1 composite foreign key
- 3 `UNIQUE` table constraints (1 `DEFERRABLE`, 2 `NULLS NOT DISTINCT`)
- 1 partitioned table (`audit_log`, PK widened) + 2 initial partitions
- 1 column type change (`user.email` → `citext`)

~102 distinct new SQL objects in total.
